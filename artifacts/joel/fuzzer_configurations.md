# Specialization A – Fuzzer Configuration

This document describes the Atheris fuzzing harnesses used to test three Tatou API endpoints. The implementations are maintained in server/test/. Campaign results and identified bugs are documented separately in [fuzzing_results.md](fuzzing_results.md) and [bugs_discovered.md](bugs_discovered.md).

## Overview

| Campaign | API endpoint | Fuzzer implementation | Default time limit | Maximum input length |
|---|---|---|---:|---:|
| A-01 | `POST /api/upload-document` | [test_fuzz_atheris_a01.py](../../server/test/test_fuzz_atheris_a01.py) | 60 s | 4,096 bytes |
| A-02 (initial) | `POST /api/create-watermark` | [test_fuzz_atheris_a02.py](../../server/test/test_fuzz_atheris_a02.py) | 60 s | 256 bytes |
| A-02 (extended) | `POST /api/create-watermark` | [test_fuzz_atheris_extended_a02.py](../../server/test/test_fuzz_atheris_extended_a02.py) | 60 s | 256 bytes |
| A-03 | `POST /api/login` | [test_fuzz_atheris_a03.py](../../server/test/test_fuzz_atheris_a03.py) | 60 s | 256 bytes |

All four scripts use atheris.Setup(...) and atheris.Fuzz() to invoke the fuzzing harness. Requests are issued to the Flask application through app.test_client(). A-01, extended A-02, and A-03 instrument project imports through atheris.instrument_imports(); the initial A-02 harness does not.

## A-01 – PDF Upload

Fuzzer: [test_fuzz_atheris_a01.py](../../server/test/test_fuzz_atheris_a01.py)  
Endpoint: POST /api/upload-document

### Input generation and test scenarios

Each fuzzing iteration uses the supplied bytes in two upload requests:

1. Raw mutated input: Uploads the Atheris-generated byte sequence under the filename atheris-mutated.pdf. The harness independently checks whether the bytes constitute a parseable PDF using PyMuPDF (fitz), and records whether valid or invalid content was accepted.
2. Generated valid PDF: Creates a one-page PDF containing a hexadecimal representation of up to the first 128 input bytes, then uploads it as atheris-valid.pdf. A rejected valid PDF raises an assertion.

The harness also treats HTTP 5xx responses during raw-input uploads as test failures. Before fuzzing, it runs six baseline checks covering plain text, empty input, a malformed PDF, a valid PDF, missing authentication, and an invalid bearer token.

### Setup and Atheris options

- Creates and logs in a unique test account, using its bearer token for upload requests.
- Uses server/test/seed_valid_a01.pdf as a seed, copied into server/test/corpus_a01_valid/ when absent from that corpus directory.
- Uses -max_total_time=60, -max_len=4096, and -print_final_stats=1.
- Prints progress counters every 1,000 completed harness iterations.
- Removes documents created for its test account after each iteration, and registers cleanup of the test account at process exit.

## A-02 – Create Watermark

Initial fuzzer: [test_fuzz_atheris_a02.py](../../server/test/test_fuzz_atheris_a02.py)  
Extended fuzzer: [test_fuzz_atheris_extended_a02.py](../../server/test/test_fuzz_atheris_extended_a02.py)  
Endpoints: POST /api/create-watermark/<document_id> and POST /api/create-watermark

### Initial harness

The initial A-02 harness creates two authenticated users and uploads a valid PDF belonging to one of them. It first verifies that the owner can create a watermarked version, then clears that version before fuzzing.

For each nonempty Atheris input, FuzzedDataProvider generates or chooses the recipient, secret, key, optional position, and whether the document ID is passed in the URL or JSON body. The method is held at visible-hmac. The request is sent as the non-owner, allowing the harness to test whether a user can create a version of another user's document.

The harness checks both the HTTP response and the number of corresponding rows in the Versions table. It counts unauthorized creations, denied requests, and other responses, printing checkpoints every 100 cases. Any created versions are cleared after each input.

Atheris options: -max_total_time=60, -max_len=256, -print_final_stats=1.

### Extended harness

The extended harness uses the same two-user, one-document setup but exercises six scenarios:

| Scenario | Behavior tested |
|---|---|
| owner_valid | Document owner submits valid watermarking parameters |
| nonowner_valid | Another authenticated user submits valid parameters |
| unauth_valid | Request is sent without authentication |
| owner_invalid | Owner submits an invalid parameter value |
| nonowner_invalid | Non-owner submits an invalid parameter value |
| missing_doc | Request references a nonexistent document ID |

It varies the route used to specify the document ID (URL path or JSON body), optional position, and input strings. For invalid scenarios, the harness rotates through the fields method, intended_for, secret, and key, supplying values such as None, an empty string, numbers, booleans, lists, and objects.

The harness records status codes, successful owner requests, unauthorized creations, and unexpected HTTP 5xx responses. It also checks the Versions table after requests, prints checkpoints every 500 cases, and removes generated versions between cases.

Default Atheris options: -max_total_time=60, -max_len=256, -print_final_stats=1. The script only adds a default option if that option was not supplied on the command line.

## A-03 – Login

Fuzzer: [test_fuzz_atheris_a03.py](../../server/test/test_fuzz_atheris_a03.py)  
Endpoint: POST /api/login

### Input generation and test scenarios

The harness creates a unique test user and verifies that a normal login succeeds before starting fuzzing. For each nonempty input, FuzzedDataProvider selects one of ten scenarios:

| Scenario | Input behavior |
|---|---|
| valid_login | Correct email and password |
| missing_email | Password provided without email |
| missing_password | Email provided without password |
| missing_both | Empty JSON object |
| wrong_password | Known email with incorrect password |
| unknown_email | Unknown email with known password |
| mutated_email | Fuzz-generated email string |
| mutated_password | Fuzz-generated password string |
| malformed_field_type | Non-string value for email or password |
| non_object_json | Top-level JSON body that is not an object |

The malformed-field scenario rotates between email and password and through values including None, numbers, booleans, lists, and objects. The non-object scenario rotates through JSON arrays, strings, numbers, and booleans.

The harness records HTTP status codes and checks that successful logins return a string token and integer expires_in, that valid credentials continue to work, and that missing or incorrect credentials are rejected. HTTP 5xx responses and unexpected behaviors are recorded with example inputs without terminating the fuzzing campaign. Progress is printed every 500 cases.

### Atheris options and cleanup

- Uses -max_total_time=60, -max_len=256, and -print_final_stats=1 as defaults, while allowing explicitly supplied values for those options.
- Registers cleanup of the unique test user at process exit.

## Test Environment

The fuzzing harnesses used Python dependencies including Atheris, Flask, PyMuPDF, and SQLAlchemy.

The Atheris campaigns were executed in a Docker-based Linux environment because installing Atheris directly on macOS encountered compatibility issues with the local build environment.

The harnesses required a functioning Tatou database and file-storage configuration, as they created test users and documents and exercised real database-backed application behavior.

## Baseline Tests

Baseline tests were used alongside the Atheris campaigns
to check API behavior using predefined inputs.

For A-01, six baseline checks were implemented directly in
[test_fuzz_atheris_a01.py](../../server/test/test_fuzz_atheris_a01.py)
and executed before fuzzing began. These covered valid and
invalid PDF content and authentication scenarios.

For A-02, a separate
[test_baseline_a02.py](../../server/test/test_baseline_a02.py)
script was used to check watermark creation by a document
owner and another authenticated user. It also examined
whether unauthorized watermark versions were created.

For A-03, a separate
[test_baseline_a03.py](../../server/test/test_baseline_a03.py)
script was used to check eight predefined login scenarios,
including valid credentials, missing fields, incorrect
credentials, and invalid JSON data types.

These baseline checks complemented the fuzzing campaigns.
The non-regression tests developed to verify the implemented
fixes are documented separately in
[non_regression_tests.md](non_regression_tests.md).
